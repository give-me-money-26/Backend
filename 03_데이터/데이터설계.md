# 03 데이터 설계

## 테이블

### `buildings`

지도와 3D 모델 선택에 필요한 건물 메타데이터입니다. `priority_rank`는 테스트 자료상의 순서이지 실제 설치 추천 등급이 아닙니다.

### `hourly_wind_densities`

건물별 시간과 풍력 에너지 밀도입니다. 현재 자료는 모두 `source_type=TEST_PDF`입니다. `(building_id, hour_of_day)`는 중복될 수 없습니다.

### `measurements`

향후 현장 조사 데이터를 원본 단위로 보관합니다. 기획안의 필수 레코드인 `building_id`, `vent_id`, `measured_at`, `timezone`, `wind_speed_m_s`, `vent_area_m2`, `sensor_id`, `quality_flag`, `operating_state`를 모두 포함합니다.

## 테스트 데이터와 실측 데이터의 경계

- 기존 5개 건물 수치는 `hourly_wind_densities`에만 보관하며 실측이라고 표시하지 않습니다.
- 현장에서 센서로 얻은 값만 `measurements`로 등록합니다.
- 결측값은 행 부재로 표현하며 0을 자동 삽입하지 않습니다.
- 시간은 오프셋이 포함된 ISO-8601 값과 IANA 시간대(예: `Asia/Seoul`)를 함께 저장합니다.
- `VALID`, `SUSPECT`, `INVALID` 품질 상태를 통해 원본을 삭제하지 않고 분석 포함 여부를 결정할 수 있습니다.

## 운영 DB 전환 시

H2는 전시·개발용입니다. 운영 시 PostgreSQL 드라이버와 접속 환경변수를 추가하고 동일한 Flyway 파일을 적용합니다. 센서 중복 업로드 방지를 위해 운영 전 `(sensor_id, measured_at)` 고유 키 정책도 확정해야 합니다.
